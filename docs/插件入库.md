# 插件入库：`插件工作区/` → `TheYjh/dsh-plugins`

这里说的是**插件**，不是模组。模组走 `./deliver` 归档进 `成品/`（见 `.agents/skills/deliver/SKILL.md`）；插件是 DSH 的扩展，成品不在本仓库里，而是发布到另一个仓库 [`TheYjh/dsh-plugins`](https://github.com/TheYjh/dsh-plugins)。

## 为什么要有这条路

插件的开发在 `插件工作区/` 里进行，但这个目录**不入库**（它是其他工作区的产物接收区，见 `AGENTS.md` 的「工作区边界」），而且每个插件的源码也各自是独立的包。发布的目标是另一个 GitHub 仓库。手工做这件事意味着：

- 记住哪些目录该发布、哪些不该（第三方克隆）；
- 每次发布前逐文件对比，还要记得删掉源里已经删了的文件（否则仓库越积越脏）；
- 手抄根 README 那张表（漏一行就少一个入口）；
- commit + push 的失败处理。

`./deliver-plugin` 把这四件事收成一条命令，并且和 `./deliver` 一个风格：**先算计划，再动手**，`--check` 一个字节都不改。

## 用法

```bash
bash deliver-plugin --check      # 只报告：会新增/更新/不变什么、删什么、README 表格变不变
bash deliver-plugin              # 同步 → 重建 README 表格 → commit → push
bash deliver-plugin --no-push    # 同步 + commit，不 push
bash deliver-plugin profile-doctor workbuddy-balancer   # 只处理点名的目录
bash deliver-plugin -h           # 打印脚本头部注释
```

脚本在 Android/Debian 的 bind mount 上，`chmod +x` 不生效，所以**一律用 `bash deliver-plugin` 调用**，不要指望 `./deliver-plugin`。

| 环境变量 | 默认 | 作用 |
|---|---|---|
| `DSHBOX_PLUGIN_SRC` | `$ROOT/插件工作区` | 同步源（每个子目录 = 一个插件） |
| `DSHBOX_PLUGIN_REPO` | `/root/share/dsh-plugins` | 插件仓库的本地克隆 |

`DSHBOX_PLUGIN_REPO` 不存在时脚本会自己克隆 `https://github.com/TheYjh/dsh-plugins.git`。克隆前会先 `git -c http.version=HTTP/1.1`——本机的 GnuTLS 走 HTTP/2 会失败。克隆失败时脚本 `die` 并打印手工命令，照着敲即可。

## 输出怎么读

对每个插件目录一行，四态：

```
源目录：/root/share/DSHBox/插件工作区
插件仓库：/root/share/dsh-plugins

同步计划（相对路径 + 内容 sha256 比对）：
  [跳过] whale-src：自带 .git（第三方克隆），不自动入库
  [新增] profile-doctor（包 dsh-profile-doctor 0.1.0）
    删除多余文件：profile-doctor/lib/old.js
  [更新] workbuddy-balancer（包 dsh-workbuddy-balancer 0.1.0）
  [不变] some-plugin（包 dsh-some-plugin 1.0.0，内容一致）

README 表格：将重建（3 个插件）

新增 1 个，更新 1 个，不变 1 个，跳过 1 个
```

- `[新增]` —— 目标仓库里还没有这个目录。
- `[更新]` —— 目录在，但「相对路径 → 内容 sha256」清单对不上（有文件改了/加了/删了）。
- `[不变]` —— 清单逐行相同，**不产生任何改动**，也不会因此造一次空提交。
- `[跳过]` —— 见下一节。

比对的单位是**文件内容**，不是 mtime、也不是 `git status`。所以 `touch` 一下不会触发同步，改一个字节就会。

## 哪些插件会被跳过

**自带 `.git` 的目录一律跳过。** 判定理由很直接：那说明它是别人的仓库克隆，不是我们写的插件，自动入库等于替原作者再许可一次。

当前 `插件工作区/whale-src/` 就是这种情况（上游 `MeteorNOX/DeepSeek-Balance-Whale-Widget`，`assets/` 下的美术素材明确不授权再许可）。脚本会打印一行

```
[跳过] whale-src：自带 .git（第三方克隆），不自动入库
```

**跳过必须被看见**，不是静默过滤：统计行里的「跳过 N 个」也是同一个信息。要把某个第三方插件收进自己的仓库，只有一条路——先确认许可证允许，再把文件**手工**搬成一个没有 `.git` 的新目录，然后它才会被当成自研插件处理。这件事脚本不替你做决定。

## 文件镜像语义

复制规则：除 `.git`、`node_modules`、`.profile-doctor`、`*.log` 之外的全部文件。

**目标侧是镜像**：源里没有的已存在文件会从目标仓库删掉。删除走 `git rm --cached --ignore-unmatch` + `rm -f`，和 `./deliver --prune` 同款——**删除进提交，旧内容永远能 `git show` 取回**，历史只前滚。

这里没有 `./deliver --prune` 那样的显式授权开关。原因不同：`成品/模组/` 里的 jar 可能是无源码资产，删了就造不出来；插件目录是源码镜像，源里有的才该在，源里删掉的就是真的不要了。如果你想要「删除也要显式授权」，那是要改脚本语义，不是加个 flag 就完事，得先讨论。

目录名用的是**源目录名**，不是 `package.json` 的 `name`。`profile-doctor/` 里的 `name` 是 `dsh-profile-doctor`，但仓库里那层目录就叫 `profile-doctor`——保持和源一致，才能让「源 | 目标」一眼对得上。

## README 表格的那对标记

插件仓库根 `README.md` 里有一张表：

```markdown
| 插件 | 包名 | 一句话 |
|---|---|---|
| [`profile-doctor`](./profile-doctor/) | `dsh-profile-doctor` | 体检 DSH profile 的声明是否完整。 |
```

脚本改的只是**表体**，靠一对 HTML 注释定位：

```markdown
<!-- plugins-table:begin -->
| 插件 | 包名 | 一句话 |
|---|---|---|
...
<!-- plugins-table:end -->
```

- 标记**必须存在**，缺了脚本 `die` 并提示手工补。没有标记时不敢猜「哪张表是插件表」，猜错就是删别人的文档。
- 标记之外的内容一个字节都不动——每个插件的小节、许可证说明、安装步骤都留在原处。
- 表头 `| 插件 | 包名 | 一句话 |` 固定不变。
- 表内容**只从 `package.json` 推导**：目录标签取 `name` 去掉 `dsh-` 前缀，一句话取 `description` 的**首句**（中文按 `。！？；` 断，英文按 `. ` 断）。不读各插件 README 的细节，也不读 `version`。
- 渲染的是「**同步后的仓库样子**」而不是「本次点名的插件」：`bash deliver-plugin profile-doctor` 只处理一个目录，但表格里其他插件那些行不会被抹掉。
- 全部插件都被跳过时（比如只点名了第三方克隆），表格保持原样，绝不清空。

首次配置插件仓库时，手工在表格上下各加一行标记即可。

## watcher：不落地的 hooks

容器里**没有** `cron`、`systemd`、`inotifywait`、`fswatch`、`entr`（`command -v` 全部失败）。所以「文件一改就自动同步」只能靠轮询。

```bash
# 后台起一个，每 5 秒看一次，变化后 2 秒 debounce 再同步
bash tools/plugin-watch.sh &

# 只跑一轮就退（给测试和一次性同步用）
bash tools/plugin-watch.sh --once
```

| 环境变量 | 默认 | 作用 |
|---|---|---|
| `DSHBOX_PLUGIN_WATCH_INTERVAL` | `5` | 轮询间隔（秒） |
| `DSHBOX_PLUGIN_SRC` | `$ROOT/插件工作区` | 透传给 `deliver-plugin` |
| `DSHBOX_PLUGIN_REPO` | `/root/share/dsh-plugins` | 透传给 `deliver-plugin` |

行为要点：

- 指纹算法与被跳过的目录**同一套规则**：只看 `$SRC` 下一级目录，跳过带 `.git` 的，其余按「相对路径 + 内容 sha256」整体再 sha256 一次。
- 指纹变了先 `sleep 2` 再取一次确认（debounce），避免编辑器保存到一半就同步。
- 日志追加到 `$ROOT/.plugin-sync.log`（已进 `.gitignore`）。每轮的开始/成功/失败各一行，带时间戳。
- **单轮失败不退出循环**：push 失败时下一轮还能重试，只是日志里多一行。只有收到 `INT`/`TERM` 才退，退之前打印一行「收到停止信号，退出。」。
- `--once` 不比对指纹，直接同步一轮（一次性调用没有基线），退出码沿用 `deliver-plugin` 的。

停止：

```bash
# 前台起的话 Ctrl-C 就行（会打印停止行）
kill -TERM <pid>
```

### 没有 cron/systemd 的现实后果

进程不是常驻服务：**它随会话结束而死**，容器重启、日志关掉、shell 退了，watcher 就没了。没有守护进程会把它拉起来。

这意味着：

1. 它是**便利设施**，不是保证。真正的保证是「手动 `bash deliver-plugin`」这条命令本身。
2. 长时间没盯着的改动不会自动发布。开工时检查一下 `pgrep -f plugin-watch.sh`，没有就重新起一个。
3. 别把它当 CI。要「提交即发布」，得在外面的 runner 上做，那不在本仓库范围内。
4. 因为它随会话死，日志文件也可能断在中间——那不代表同步失败，`bash deliver-plugin --check` 一看就知道真实状态。

## 失败处置

| 现象 | 原因 | 怎么办 |
|---|---|---|
| `README.md 缺少表格起始标记` | 插件仓库的 README 没加标记 | 手工在表格上下各补一行标记，再跑 |
| `package.json 缺失、不是合法 JSON，或缺少 name/version —— 整批拒绝` | 有插件的 `package.json` 不合格 | 修好那个 `package.json`，再跑。**不会**有「复制了一半」的中间状态 |
| `目标仓库不存在，正在克隆` 之后失败 | 网络/凭据问题 | 按脚本打印的手工命令克隆；确认 `git -C <REPO> remote -v` 指向对的仓库 |
| `推送失败（已重试 2 次）。本地提交已保留，未回滚。` | 网络或远端拒绝 | **本地提交不会丢**。确认网络后 `git -C /root/share/dsh-plugins push`。下次 `deliver-plugin` 也会自动补推未推送的提交 |
| 目标仓库缺少 `README.md` | 克隆不完整 | 检查克隆；插件仓库的 README 是必需的 |
| 目标仓库里某个 `package.json` 读不出来 | 有人手改了目标仓库 | 先把那个文件修好再同步，脚本拒绝在信息不全时重建表格 |

退出码：`0` 成功（含 `--check`），`1` 业务失败（校验/克隆/推送），`2` 未知选项。

## 与 `./deliver` 的关系

| | `./deliver` | `./deliver-plugin` |
|---|---|---|
| 归档什么 | `dist/*.jar` → `成品/模组/` | `插件工作区/*/` → 插件仓库 |
| 提交到哪 | 本仓库 | `TheYjh/dsh-plugins` |
| 比对键 | 内容 sha256 + 目标文件名 | 相对路径 → 内容 sha256 清单 |
| 删除 | 默认只报告，`--prune` 才删 | 镜像，默认删 |
| 推送 | 三次重试后保留本地提交 | 同样 |

两者互不干扰：`./deliver` 只 `git add` `成品/`、`GLOSSARY.md`、`NAMING.md`；`./deliver-plugin` 完全在另一个仓库里干活。

新用例在 `tests/cases/7*.sh`，夹具库是 `tests/lib/plugin-harness.sh`（和 `deliver` 的 `harness.sh` 互不污染）。全程离线：目标仓库的 origin 是 `git init --bare` 造的本地裸仓库。

```bash
bash tests/run.sh            # 全部
bash tests/run.sh '7*'       # 只跑插件同步那几条（glob 是整名匹配，要带 *）
```

用例覆盖：归档并提交、跳过第三方克隆、`--check` 零改动、内容不变不造空提交、镜像删除多余文件。`BUILD.md` 的用例表里有逐条说明。
